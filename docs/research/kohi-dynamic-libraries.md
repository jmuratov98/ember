# How Kohi splits itself into dynamic libraries

**Question** (jmuratov98/ember#2, "How does Kohi split itself into dynamic libraries?"): How does Travis Vroman's Kohi engine split itself into dynamic libraries? Which parts are separate libraries? How are they found and loaded? How does code call across library boundaries? How is the game split from the engine, and how does hot reload work? How does the build produce `.dll`/`.dylib`/`.so` files? What trade-offs has the author called out? What can Ember borrow?

**Kohi version examined:** GitHub mirror commit [`05a5193d5ed4890703cfcbbeb5c5e947feefecf6`](https://github.com/travisvroman/kohi/tree/05a5193d5ed4890703cfcbbeb5c5e947feefecf6) ("Mirror SVN revision r96", committed 2026-10-29). Every module's `version.txt` reads `v0.14.0`. Since the SVN move, GitHub is only a mirror ([readme L17-L22](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L17-L22)). On 2026-11-08 SVN `trunk` was at r108. I compared 11 key files byte for byte between the mirror and `https://svn.kohiengine.com/svn/kohi/trunk`, and all were identical: `Makefile`, `Makefile.prefix`, `engine.c`, `plugin_system.c`, `plugin_types.h`, `platform_nix.c`, `platform_win32.c`, `defines.h`, both testbed Makefiles, and `app_config.kson`. ## Summary

- **Almost everything is a shared library.** Kohi builds 7 shared libraries (`kohi.core`, `kohi.runtime`, four `kohi.plugin.*`, and the game library `testbed.klib`) plus thin executables (`testbed.kapp`, `kohi.tools`, the test runners). Nothing in Kohi's own code is built as a static archive. The platform layer is not a separate library: it lives inside `kohi.core`, and a roadmap item to split it out is still open.
- **Two ways of loading.** (1) Normal link-time dependencies: `-lkohi.core -lkohi.runtime ...`, which the OS loader resolves through rpath `$ORIGIN` / `@rpath` / the exe's directory. (2) Loading by name at runtime with `LoadLibraryW`/`dlopen`, through one platform API in `kohi.core`: `platform_dynamic_library_load(name)`. That function adds `lib` + `.so`/`.dylib` or `.dll` to the name. Plugins and the game library are loaded the second way.
- **Plugins are listed in config, not discovered.** `app_config.kson` lists the plugin names (`kohi.plugin.renderer.vulkan`, ...). Each frontend system picks its backend with a `backend_plugin_name` key. Nothing scans a directory: the libraries are expected next to the exe in `bin/`.
- **Plugins use name-derived exported entry points.** The plugin system turns the library name into a symbol prefix (`.` becomes `_`). It looks up `<prefix>_create` and `<prefix>_destroy` (both required) plus optional hooks (`_boot`, `_initialize`, `_update`, `_frame_prepare`, `_render`, `_on_window_resized`) and stores them in a `kruntime_plugin` struct.
- **Backends hand the engine a function-pointer table.** The Vulkan plugin's `_create` allocates a `renderer_backend_interface` (about 100 function pointers, defined in `kohi.runtime`), fills it in, and stores it as `plugin_state`. The renderer frontend casts it back and calls through it. OpenAL does the same with `kaudio_backend_interface`.
- **Calls in the other direction are plain linked symbols.** Plugins and the game call `kohi.core`/`kohi.runtime` functions (`kallocate`, `renderer_renderbuffer_create`, `engine_systems_get`, ...) directly through link-time imports. Symbols are hidden by default (`-fvisibility=hidden`) and exported with one `KAPI` macro (`__declspec(dllexport)` or `visibility("default")`). Kohi exports no global variables; engine state is reached through getter functions.
- **The game is a hot-reloadable library behind a tiny exe.** `testbed.kapp`'s source is two functions (config path and klib name). `main()` comes from the runtime header `entry.h`. The engine copies `testbed.klib` to `testbed.klib_loaded`, loads that copy, and resolves 10 fixed `application_*` symbols. It then watches the original file each frame (mtime polling). On change it calls `application_lib_on_unload`, unloads, re-copies, reloads, and calls `application_lib_on_load`. Game state survives because it lives in engine-owned memory. Only the game library hot-reloads; plugins do not.
- **The build is hand-written Make + clang on all three OSes.** One shared `Makefile.prefix` turns `ASSEMBLY_IS_SHARED=true` into `-shared -DKEXPORT` with `.dll` (Windows), `lib*.so` + `-fPIC` + `--no-undefined` + `-rpath=$ORIGIN` (Linux), or `lib*.dylib` + `-dynamiclib` + `-install_name @rpath/...` (macOS). Each module builds into its own `bin/`, and the root Makefile copies everything into one top-level `bin/`.
- **The architecture changed in steps.** Day one (Feb 2021): `engine.dll` + exe. Jan–Feb 2023: Vulkan moved into its own DLL plugin, game code moved into a lib, hot reload added. v0.7.0: split into `kohi.core` + `kohi.runtime`, a config-driven plugin system with generic `kplugin_create` symbols, and the `kohi.*` names. v0.11.0: plugin symbols prefixed by name, and game-lib loading and hot reload moved from the exe into the runtime. Later: Vulkan and OpenAL themselves loaded at runtime instead of linked.
- **Pain points the author recorded:**
  - Linux silently allows undefined symbols in shared libraries, so he passes `--no-undefined`.
  - macOS does not search `/usr/local/lib`, so the readme suggests a symlink workaround, and the exe must be run from `bin/`.
  - Hot reload was fragile because of callbacks pointing into the old library; he reworked keymaps into action codes to have fewer of them.
  - The 2023 hot-reload work included a Windows PDB cleanup commit.
  - Shutdown order forced a `block_auto_unload` workaround for the renderer plugin.
  - Deciding where `shaderc` gets linked runs into "yet another plugin that has to be distributed".

Static linking: every Kohi module is either a shared library or an executable. Each module's `.c` files are compiled into its own binary ([Makefile.prefix L119-L121, L233-L234](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L233-L234)), and no Makefile builds a static archive. The only code compiled straight into the exe is `main()`. It lives in the runtime header `entry.h`, which the app's `entry.c` `#include`s ([kohi.runtime/src/entry.h L49-L73](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/entry.h#L49-L73)). Third-party libraries are linked dynamically too: assimp's DLL is copied into `bin` ([Makefile L100](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile#L100)), and `libshaderc_shared.so` is copied on Linux ([L115-L117](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile#L115-L117)).

Where the module boundaries sit: the renderer and audio **frontends** live inside `kohi.runtime`, and only the **backends** are plugins. On macOS, Kohi renders through Vulkan via MoltenVK (`VK_USE_PLATFORM_MACOS_MVK` is defined in core, marked `// HACK` in [defines.h L185-L186](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/defines.h#L185-L186)). Direct3D, Metal, OpenGL and headless renderer plugins are unchecked roadmap items ([TODO.md L198-L211](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L198-L211)). The roadmap also carries the open item "Split off platform layers into separate libraries outside the engine." ([TODO.md L233](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L233)). Kohi has no physics module.

### 2. How libraries are loaded and discovered

#### 2a. Link-time (implicit) loading

`kohi.core`, `kohi.runtime`, `kohi.plugin.ui.kui` and `kohi.plugin.utils` are named on the link line of the libraries and exes that use them (table above), so the OS loader maps them at process start. How each platform finds them:

- **Linux:** every module links with `-Wl,--no-undefined,--no-allow-shlib-undefined,-rpath='$ORIGIN'` ([Makefile.prefix L122-L126](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L122-L126)), so dependencies are found next to the binary that needs them.
- **macOS:** shared libraries get `-install_name @rpath/lib<name>.dylib`, and executables get `-Wl,-rpath,.` ([Makefile.prefix L154-L162](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L154-L162)). That rpath is the current working directory, not `@executable_path`.
- **Windows:** no special flags. DLLs sit next to the exe in `bin/`.

The root Makefile copies every module's `bin/*` into one top-level `bin/` ([Makefile L85-L119](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile#L85-L119)). The readme says: "You _must_ be within the `bin` working directory for pathing to work properly when loading assets!" ([readme L159](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L159)).

#### 2b. Runtime (explicit) loading: one platform API

`kohi.core` exports `platform_dynamic_library_load/unload/load_function/extension/prefix` ([platform.h L32-L41, L367-L394](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform.h#L367-L394)). The library handle is a `dynamic_library` struct holding the name, filename, OS handle, a file-watch id and a darray of resolved functions.

- **Windows** ([platform_win32.c L712-L809](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_win32.c#L712-L809)): `LoadLibraryW("<name>.dll")`, `GetProcAddress`, `FreeLibrary`. The prefix is `""`; the extension is `.dll`.
- **Linux and macOS** share one implementation ([platform_nix.c L14, L405-L531](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_nix.c#L405-L473)). It builds `lib<name><ext>` and calls `dlopen(..., RTLD_NOW)` over a fixed list of 11 path formats: bare name, `./`, `/lib/`, `/usr/local/lib/`, `/usr/lib64/`, `/lib/x86_64-linux-gnu/`, each also with a `.1` suffix. For each path it retries with the raw name (no prefix or extension). The extension is `.so` on Linux ([platform_linux.c L1084-L1090](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_linux.c#L1084-L1090)) and `.dylib` on macOS ([platform_macos.m L767-L773](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_macos.m#L767-L773)), both with prefix `lib`.

Three groups of libraries are loaded through this API:

1. **Engine plugins**, from config. `engine_create` reads the `plugin_system` block of `app_config.kson` ([engine.c L445-L468](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L445-L468)). It loads every listed plugin by name *before* the renderer and audio systems initialize ([plugin_system.c L93-L118](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/systems/plugin_system.c#L93-L118); design note in [plugin_system.h L19-L24](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/systems/plugin_system.h#L19-L24)). Testbed's list is `kohi.plugin.ui.kui`, `kohi.plugin.utils`, `kohi.plugin.renderer.vulkan` and `kohi.plugin.audio.openal`; each entry can carry an optional `config` object that is passed to the plugin as a string ([app_config.kson L118-L142](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.kapp/app_config.kson#L118-L142)). Frontends then pick their backend by name. The renderer config has `backend_plugin_name = "kohi.plugin.renderer.vulkan"` ([L74-L80](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.kapp/app_config.kson#L74-L80)), and `renderer_system_initialize` calls `plugin_system_get(..., backend_plugin_name)` ([renderer_frontend.c L190-L208](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/renderer/renderer_frontend.c#L190-L208)). Audio works the same way ([audio_frontend.c L307](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/audio/audio_frontend.c#L307); [app_config.kson L33-L35](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.kapp/app_config.kson#L33-L35)). There is no directory scan or manifest of available plugins.
2. **The game library.** The exe supplies its name (`"testbed.klib"`, [testbed.kapp/src/entry.c L8-L14](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.kapp/src/entry.c#L8-L14)). The engine loads a copy named `<name>_loaded` (section 4).
3. **Third-party system libraries, loaded by the plugins.** The Vulkan plugin loads `vulkan-1` / `vulkan` / `vulkan.1` ([win32 L78](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/platform/vulkan_platform_win32.c#L78), [linux L85](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/platform/vulkan_platform_linux.c#L85), [macos L88](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/platform/vulkan_platform_macos.c#L88)) and resolves functions with a macro ([vulkan_loader.c L11](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/vulkan_loader.c#L11)). The plugin changelog records this: "Changed linking of Vulkan lib to dynamic, and added a custom loader." ([vulkan CHANGELOG L19](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/CHANGELOG#L19)). OpenAL is loaded from `OpenAL.framework` / `libopenal.so.1` / `OpenAL32` ([openal_backend.c L500-L516](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.audio.openal/src/openal_backend.c#L500-L516)); the 0.14.0 changelog says "OpenAL plugin now dynamically links OpenAL." ([CHANGELOG L3-L4](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/CHANGELOG#L3-L4)).

`kohi.plugin.ui.kui` and `kohi.plugin.utils` are **both** link-time dependencies of `testbed.klib`/`testbed.kapp`/`kohi.tools` **and** listed as runtime plugins. The game calls KUI functions directly, for example `kui_label_control_create` ([testbed_main.c](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.c#L229)). It also gets KUI's state through the plugin registry: `plugin_system_get(..., "kohi.plugin.ui.kui")->plugin_state` ([testbed_main.c L155-L163](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.c#L155-L163)). So a "plugin" in Kohi can also be a normal linked library. Only the renderer and audio backends are linked by nothing and reachable only through the plugin system.

### 3. How code calls across library boundaries

#### 3a. Exported symbols (`KAPI`)

- Every module compiles with `-fvisibility=hidden`, commented "hides all symbols by default, and only those that explicitly say otherwise are exported (i.e. via KAPI)" ([Makefile.prefix L22-L23](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L22-L23)).
- Shared libraries get `-DKEXPORT` and executables get `-DKIMPORT` ([Makefile.prefix L104-L111, L132-L139, L154-L162](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L104-L111)).
- `KAPI` expands to `__declspec(dllexport)` / `__attribute__((visibility("default")))` under `KEXPORT`, and otherwise to `__declspec(dllimport)` / nothing ([defines.h L195-L211](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/defines.h#L195-L211)).
- *Observation (mine, not the author's):* there is one `KAPI` macro for the whole project, not one per library. So when `kohi.runtime` includes `kohi.core` headers, those declarations also expand to `dllexport`; `dllimport` only appears in executables. Kohi builds and runs this way (with clang/lld on Windows), but it means a library cannot tell "my exports" apart from "someone else's imports".

These exports are what most cross-library calls go through. The Vulkan plugin, for example, calls `kallocate`/`kfree`/`darray_*` (core) and `renderer_renderbuffer_create`, `renderer_default_texture_get`, `engine_systems_get`, `event_fire` (runtime) directly. The OS loader resolves them through the `-lkohi.core -lkohi.runtime` dependencies.

Engine-wide state is exposed through exported getters (`engine_systems_get()` returns a struct of every system's state pointer; also `engine_frame_data_get`, `engine_app_state_get`, `engine_external_system_register/_state_get`; [engine.h L50-L164](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.h#L50-L164)). I found no exported global variables. There is one memory system (`kallocate`/`kfree` in `kohi.core`), and plugins and the game allocate from it.

#### 3b. Plugin entry points, resolved by a name convention

`plugin_system_load_plugin` ([plugin_system.c L221-L302](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/systems/plugin_system.c#L221-L302)) works like this:

1. Load the library by its configured name.
2. Build a symbol prefix by replacing `.` with `_`, so `kohi.plugin.renderer.vulkan` becomes `kohi_plugin_renderer_vulkan`.
3. Look up `<prefix>_create` and `<prefix>_destroy`; both are required (`KFATAL` if missing).
4. Look up the optional `_boot`, `_initialize`, `_update`, `_frame_prepare`, `_render` and `_on_window_resized`.
5. Call `_create`, then `_boot`, and push the plugin into a registry that `plugin_system_get(name)` searches.

The engine calls `_initialize` on all plugins after the game's `application_boot` ([engine.c L763-L777](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L763-L777)), and the update/frame-prepare hooks every frame. The `kruntime_plugin` struct holds the name, config string, `dynamic_library`, hook pointers, `plugin_state` and a `block_auto_unload` flag ([plugin_types.h L22-L91](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/plugins/plugin_types.h#L22-L91)). Its doc comment is out of date: it still says the plugin "must have an exported function called 'kplugin_create'" ([L39-L42](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/plugins/plugin_types.h#L39-L42)), which was the convention before v0.11 (section 6). The exported entry points are declared with `KAPI` in each plugin's `*_main.h`: [Vulkan](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/vulkan_renderer_plugin_main.h#L22-L29), [OpenAL](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.audio.openal/src/plugin_audio_main.h#L19-L20), [KUI](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.ui.kui/src/kui_plugin_main.h#L27-L36), [utils](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.utils/src/utils_plugin_main.h#L16-L18).

#### 3c. Backend interfaces: function-pointer tables handed over at create time

`kohi_plugin_renderer_vulkan_create` allocates a `renderer_backend_interface`, assigns about 100 function pointers (`initialize`, `frame_prepare`, `shader_create`, `renderbuffer_draw`, ...), and stores it as `out_plugin->plugin_state` ([vulkan_renderer_plugin_main.c L16-L132](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/vulkan_renderer_plugin_main.c#L16-L132)). The struct is defined by the runtime ([renderer_types.h L298-L899](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/renderer/renderer_types.h#L298-L309)). It includes a `frontend_state` back-pointer and an opaque `internal_context` for the backend. The frontend "cold-casts" `plugin_state` to the interface and calls through it ([renderer_frontend.c L204-L207](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/renderer/renderer_frontend.c#L204-L207)). OpenAL fills a `kaudio_backend_interface` the same way ([plugin_audio_main.c L18-L48](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.audio.openal/src/plugin_audio_main.c#L18-L48); struct at [kaudio_types.h L62-L114](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/audio/kaudio_types.h#L62-L114)).

So the shape is: frontend → backend through a function table; backend → engine through linked exports. Nothing checks interface version or struct size between the runtime and a plugin. Per-library version strings exist ([CHANGELOG L244-L260](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/CHANGELOG#L244-L260)), but a plugin only logs its `KVERSION`.

#### 3d. Game library entry points

The engine resolves 10 fixed names from the game library into function pointers on the `application` struct. Nine are required, and any one missing aborts the load ([engine.c L1191-L1245](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L1191-L1245); struct in [application_types.h L46-L121](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/application/application_types.h#L46-L121)). The names are `application_boot`, `_initialize`, `_update`, `_prepare_frame`, `_render_frame`, `_on_window_resize`, `_on_action`, `_shutdown`, `_lib_on_load` and `_lib_on_unload`. The game declares them `KAPI` ([testbed_main.h L20-L46](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.h#L20-L46)). In the other direction, the game calls engine and plugin APIs directly through its link-time dependencies.

### 4. Game/engine split and hot reload

**The split.** The executable is a stub. `testbed.kapp/src/entry.c` only returns the config path and `"testbed.klib"` ([L8-L14](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.kapp/src/entry.c#L8-L14)). `main()`, pulled in from `entry.h`, calls `engine_create` and then `engine_run` ([entry.h L56-L73](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/entry.h#L56-L73)). The game code is all in `testbed.klib`.

**Hot reload flow** (all inside `kohi.runtime`):

1. **Startup** ([engine.c L316-L363](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L316-L363)): copy `<prefix>testbed.klib<ext>` to `<prefix>testbed.klib_loaded<ext>`, retrying every 100 ms while `platform_copy_file` returns `PLATFORM_ERROR_FILE_LOCKED`. Load the *copy* and resolve the symbols. Then `platform_watch_file` the *original* path.
2. **Detection:** watches are polled once per frame inside `platform_pump_messages` ([engine.c L835](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L835); [platform_linux.c L1001-L1002](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_linux.c#L1001-L1002)) by comparing mtimes. Linux uses `stat` and fires only after the mtime has stayed unchanged for 10 polls ([platform_linux.c L1329-L1377](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_linux.c#L1358-L1374)). Win32 (`FindFirstFileW` + `CompareFileTime`, [platform_win32.c L960-L1000](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/src/platform/platform_win32.c#L986-L999)) and macOS fire as soon as the mtime changes.
3. **Reload** ([engine.c L1247-L1290](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L1247-L1290)): call `app->lib_on_unload(app)`, unload the `_loaded` library, sleep 100 ms, copy again (with the same file-locked retry), then `load_game_lib`, which re-resolves everything and calls `lib_on_load`.

**What survives a reload:**

- The game's state survives. The game allocates it in `application_boot` through the engine's allocator, `app->state = kallocate(...)` ([testbed_main.c L120-L125](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.c#L120-L125)), and the engine keeps the `application` struct. Only the code is swapped.
- Anything the engine holds that points *into* the old library is not handled for the game. Event handlers and console commands must be removed in `application_lib_on_unload` and re-registered in `application_lib_on_load`, and the game does this explicitly ([testbed_main.c L819-L850](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.c#L819-L850), [L967-L995](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/testbed.klib/src/testbed_main.c#L967-L995)). A keymap re-registration there is still commented out as `// TODO: re-enable`.
- Nothing checks whether the layout of `application_state` changed between builds.

**Rebuilding only the game:** `build-app-lib.sh` runs `make testbed-lib-debug`, which builds `testbed.klib` and copies it into `bin/`, so the watcher fires ([build-app-lib.sh](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/build-app-lib.sh); [Makefile L121-L138](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile#L121-L138)). The Windows `build-app-lib.bat` runs `make testbed-debug` instead ([build-app-lib.bat](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/build-app-lib.bat)).

**Scope:** only the game library is hot-reloaded. Plugins are loaded once and unloaded at shutdown ([plugin_system.c L120-L137](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/systems/plugin_system.c#L120-L137)). "editor logic library (dll/.so) hot reload" is an open roadmap item ([TODO.md L230](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L230)). Asset hot reload is a separate VFS/asset-system feature built on the same file-watch API.

### 5. How the build produces .dll / .so / .dylib

The build is GNU Make with clang on all three platforms, and the readme says MSVC/Visual Studio is not supported ([readme L78-L80](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L78-L80)). Each module's Makefile sets only `ASSEMBLY_NAME`, `ASSEMBLY_IS_SHARED` and `ADDL_*` (cross-platform and per-platform defines, cflags, includes and ldflags), then includes `../Makefile.prefix`, "which actually does all the work" (e.g. [kohi.core/Makefile](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.core/Makefile)). `Makefile.prefix` sets the per-platform values ([L49-L179](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L49-L179)):

| | Windows | Linux | macOS |
|---|---|---|---|
| Shared output | `bin\<name>.dll` | `bin/lib<name>.so` | `bin/lib<name>.dylib` |
| Shared flags | `-shared -DKEXPORT` | `-shared -DKEXPORT -fPIC -pthread` | `-dynamiclib -shared -install_name @rpath/lib<name>.dylib -DKEXPORT -pthread` (+ `-arch arm64` on Apple Silicon) |
| Exe flags | `-DKIMPORT`, `.exe` | `-DKIMPORT` | `-DKIMPORT -Wl,-rpath,.` |
| Always | `-fdeclspec -Xlinker /INCREMENTAL`; MSVC and Windows SDK include and lib paths found through `vswhere` and the registry | `-Wl,--no-undefined,--no-allow-shlib-undefined,-rpath='$ORIGIN'` | — |

Linking is one `$(CC) $(OBJ_FILES) -o $(OUTPUT_NAME) $(LDFLAGS) ...` line ([L233-L234](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L233-L234)). On Windows, `-lkohi.core -L../kohi.core/bin` needs an import library next to the DLL. I assume lld-link writes it, but I did not build to confirm. Each module builds into `<module>/bin/`, and the root Makefile orders the builds as utils → core → runtime → plugins → klib → kapp, then copies everything into the top-level `bin/` ([Makefile L131-L138, L85-L119](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile#L131-L138)). A `genversion` step writes `src/<assembly>_version.h` from each module's `version.txt` ([Makefile.prefix L218-L219](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L218-L219)). Asked about the custom build, the author's FAQ says: "I do not want to be beholden to a particular build system's or IDE's way of doing things." ([kohiengine.com/faq.php](https://kohiengine.com/faq.php)).

### 7. Trade-offs and pain points

Stated by the author:

- **Linux allows undefined symbols in shared libraries by default.** The comment on the Linux flags: "`--no-undefined` and `--no-allow-shlib-undefined` ensure that symbols linking against are resolved. These are linux-specific, as the default behaviour is the opposite of this, allowing code to compile here that would not on other platforms from not being exported (i.e. Windows)" ([Makefile.prefix L122-L126](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/Makefile.prefix#L122-L126)).
- **macOS library search paths.** "On newer macOS environments, `/usr/local/lib` isn't automaticaly searched for when resolving dependencies. A quick fix for now is to symlink any missing libraries in the `bin` folder ... This will be fixed in a future version" ([readme L150-L152](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L150-L152)). The Vulkan plugin adds `-Wl,-rpath,/usr/local/lib` on Darwin ([Makefile L29](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/Makefile#L29)). Executables must be run from `bin/` ([readme L159](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L159)).
- **Hot reload and callbacks.** The roadmap item: "Rework keymaps to use game lib defined 'actions' ... handled by a single point of entry into the app instead of callbacks. This should reduce the number of callbacks needed to be refreshed on hot-reload." ([TODO.md L657-L661](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L657-L661)). That rework is why `application_on_action` exists.
- **Windows PDBs during hot reload.** The 2023 hot-reload work was followed by a "PDB cleanup on Windows" commit (above). The current Makefiles contain no PDB-specific handling.
- **Static data in the renderer DLL.** When Vulkan became a separate DLL, a dedicated pass "Removed static data from Vulkan plugin" (#124 commit message).
- **Shutdown order.** The Vulkan plugin sets `block_auto_unload = true` ("Don't let the plugin system unload this plugin. It'll be handled here instead.", [vulkan_renderer_plugin_main.c L17-L18](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.plugin.renderer.vulkan/src/vulkan_renderer_plugin_main.c#L17-L18)). The renderer frontend unloads the library itself after backend shutdown ([renderer_frontend.c L322-L327](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/renderer/renderer_frontend.c#L322-L327)). The engine shuts down "plugins, but not the system yet in case plugins which do not 'auto-unload' rely on the state still existing" ([engine.c L1040-L1056](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/core/engine.c#L1040-L1056)).
- **Which plugin links a dependency.** On moving `shaderc` out of the Vulkan plugin: "it _would_ need to be linked _somewhere_. Adding it to the utils plugin is one option, but having Vulkan-specific stuff there is strange. Could also make _another_ plugin ... has the drawback of being yet another plugin that has to be distributed" ([TODO.md L63-L67](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L63-L67)).
- **The platform layer sits inside core.** "Split off platform layers into separate libraries outside the engine." is still open ([TODO.md L233](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/TODO.md#L233)).
- **Maturity.** Kohi "is not, and will not be for quite a while, production-ready" ([readme L58](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/readme.md#L58)).

Observed in the code (my reading, not stated by the author):

- **Optional hooks are not type-checked.** They are resolved by string name through `dlsym`, so the compiler cannot check signatures. `plugin_system_on_window_resize_plugins` tests `kplugin_render` but calls `kplugin_on_window_resized`, passing the plugin where the typedef expects `plugin_state` ([plugin_system.c L208-L219](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/systems/plugin_system.c#L208-L219); typedef at [plugin_types.h L31](https://github.com/travisvroman/kohi/blob/05a5193d5ed4890703cfcbbeb5c5e947feefecf6/kohi.runtime/src/plugins/plugin_types.h#L31)).
- **No ABI or version handshake** between the runtime and the plugin interface structs.
- **One shared `KAPI` macro** for all libraries (section 3a).
- **`testbed.kapp` links `-ltestbed.klib`** even though its source uses no klib symbols, and the engine separately loads the `_loaded` copy (section 2b).

## Implications for Ember

These are options and trade-offs for the "Module system design" ticket, not a decision.

**What Kohi shows works in practice:**

- **One loading API in core** (`load`/`unload`/`symbol`/`extension`/`prefix`) that hides `LoadLibraryW`/`dlopen` and the `lib`/`.dll`/`.so`/`.dylib` naming. Everything else uses it, including backends loading their own system libraries (Vulkan loader, OpenAL).
- **The frontend/backend split.** A frontend system that owns the public API, plus backend plugins that fill in a function table defined by the frontend's headers, with the backend chosen by name from config. This fits Ember's "renderer + one library per backend" (Vulkan/Metal/D3D/GL) directly.
- **A per-module export macro and visibility setup**: `-fvisibility=hidden`, export only what's annotated, and `--no-undefined` on Linux so Linux builds fail where Windows would.
- **The game-as-library pattern** with copy-before-load and an `on_unload`/`on_load` pair, keeping state in engine-owned memory.

**Options for how far to take "every module is a DLL":**

1. **Kohi-style hybrid.** A few big link-time libraries (core with platform, engine/runtime with frontends), runtime-loaded backend plugins, and a hot-reloadable game library.
   - For: proven to work on all three desktop OSes, few libraries to manage, and an ordinary C API between core and runtime.
   - Against: platform and renderer are not separate libraries. Ember's stated goal goes further than Kohi does here, and Kohi's own TODO wants the platform split out.
2. **Every module its own shared library, all linked at build time** (core, platform, renderer, audio, physics...), with only backends and the game loaded at runtime.
   - For: simple, because the OS loader resolves dependencies, calls are plain function calls, and it is easy to debug.
   - Against: load order and dependencies are fixed at link time, so a module can't be dropped without relinking. You need a per-module export macro (Kohi's single `KAPI` would not separate modules), and rpath/install-name care on every library (`$ORIGIN`, `@rpath` with `@loader_path`/`@executable_path` rather than Kohi's CWD-relative `.`).
3. **Every module loaded at runtime through one entry symbol** that returns a versioned API table (a generalization of Kohi's `<name>_create` plus a function table).
   - For: modules can be swapped or omitted by config, could hot-reload individually, and the boundaries are explicit.
   - Against: every cross-module call goes through a table. You need an ABI/version handshake (Kohi has none), explicit dependency ordering (Kohi hard-codes it in `engine_create`), and a policy for who owns memory (Kohi: one allocator in core). Callbacks into unloaded code have to be handled.
4. **Any of the above plus a monolithic or static build option** for shipping. Kohi has no such option, so there is no Kohi evidence on its cost.

**Cross-cutting choices Kohi forces into view:**

- **Discovery:** explicit config list (Kohi) or a directory scan or manifest.
- **Symbol naming:** generic entry names (Kohi ≤ v0.10) or name-prefixed ones (Kohi ≥ v0.11).
- **Function tables vs. direct calls** at each boundary.
- **Hot reload on Windows:** Windows locks loaded DLLs and their PDBs. Kohi copies the DLL and polls the file; it did a PDB cleanup in 2023, and the current build has no PDB-specific handling.
- **What may hold function pointers into a reloadable module:** Kohi needs explicit unregister and re-register.
- **Where backend-specific build dependencies live:** Kohi's open `shaderc` question.

- **Whether `testbed.kapp`'s `-ltestbed.klib` creates a load-time dependency.** If it does on Linux (it depends on the linker's `--as-needed` default), a second copy of the game library may load alongside `testbed.klib_loaded`. Not checked; I did not build Kohi.

- **SVN trunk r108 vs. this mirror (r96):** only the 11 files listed at the top were compared. Other files may differ.
- **No Kohi evidence on several of Ember's needs:** Metal/D3D/GL backends, separate platform or physics libraries, and plugin hot reload do not exist in Kohi, so there is no evidence about them there.
